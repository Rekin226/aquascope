# CAMELS benchmark

AquaScope provides a benchmark against the 10 CAMELS catchments in
`data/camels_benchmark/`: it runs AquaScope's own implementations of a variety
of hydrological metrics — flood frequency, baseflow separation and the full
signature set — over the benchmark data and compares every number to the published
CAMELS attributes and to an independent reference computed with scipy / lmoments3.
One `results.json` is the single source of truth; `results.md` and `results.html`
are renderings of it.

Two scripts, neither is needed to use AquaScope itself:
- `benchmarks/fetch_peak_flows.py` — fetches the USGS NWIS annual-peak series,
  screens them, fits GEV-MLE / GEV-L-moments / LP3, and publishes
  `ffa_reference.json`. This is a network step and is only needed to regenerate
  the reference.
- `benchmarks/camels_benchmark.py` — the harness: runs AquaScope's methods, compares to the reference
and the published CAMELS attributes, and emits `results.json`. No network access required.


Everything local lives in `data/camels_benchmark/`: `daily_catchments.json` (the ten
published attributes), the synthetic daily catchment series (`daily/*_daily.csv`),
the flood-frequency peaks (`peaks/*.csv`) and the reference quantiles
(`ffa_reference.json`). The ten synthetic CSVs (~0.8 MB) are committed
deliberately even though `generate_synthetic.py` reproduces them byte-for-byte
from `default_rng(42)`: it buys a network-free CI, a fixed artifact to diff a
regression against, and a reader who can see what the harness ran on without
executing anything.

## How to run the benchmark locally

```bash
# 1. environment + dependencies (the [benchmarks] extra adds the
#    generation-only packages: dataretrieval and lmoments3)
python -m venv .venv
source .venv/bin/activate
pip install --upgrade pip
pip install -e ".[benchmarks]"
pip install pytest                # for the test suite below

# 2. synthetic daily catchment series (deterministic; these are already
#    committed under data/camels_benchmark/daily/, so this is only needed to
#    regenerate them)
python data/camels_benchmark/generate_synthetic.py

# 3. flood-frequency reference data (network): USGS peak series -> peaks/*.csv,
#    then GEV-MLE / GEV-L-moments / LP3 quantiles -> ffa_reference.json
python benchmarks/fetch_peak_flows.py

# 4. the report: runs every relevant AquaScope method, writes results.json,
#    results.md and results.html into benchmark-output/ (gitignored)
python -m benchmarks.camels_benchmark --output-dir benchmark-output

# 5. (optional) re-render that recorded results.json later — the reports are
#    rebuilt from the JSON, the numbers are never recomputed
python -m benchmarks.camels_benchmark --from-json benchmark-output/results.json --output-dir benchmark-output

# 6. (optional) the test suite (no network; mocks USGS)
pytest tests/test_benchmarks/
```

If the committed data is fine as-is (it always will be on a fresh clone), you
can skip steps 2–3 and go straight to `python -m benchmarks.camels_benchmark`.
The reference was computed against the USGS snapshot at fetch time, so run step
3 again whenever you want a current snapshot.

## The harness

```bash
python -m benchmarks.camels_benchmark --output-dir benchmark-output
```

Flags:

- `--gauge-id 01013500 01664000` — restrict the run to these gauges.
- `--no-reports` — write only `results.json`.
- `--strict` — exit non-zero when any recorded check is unmet.
- `--from-json PATH` — skip the run entirely and re-render an existing
  `results.json` into the output directory (`results.json` copy + `results.md`
  + `results.html`). Useful after a report layout change: the JSON stays the
  single source of truth.
- `--output-dir` (default `benchmark-output`) — where the three results files go.

### Where outputs live

- **Local runs** write to `benchmark-output/` (gitignored) by default.
- **Published examples** are committed in `examples/camels_benchmark/` and are
  intentionally NOT regenerated by a default run — a local run never overwrites
  them. To refresh them explicitly, run:
  ```bash
  python -m benchmarks.camels_benchmark --output-dir examples/camels_benchmark
  ```
  Note that every run records wall-clock `seconds` per stage, which varies from
  run to run, so regenerating the committed examples also churns those timings.

### Reports derive from the JSON

`results.md` and `results.html` (built with AquaScope's `ReportBuilder`)
only *read* the results dict: they never recompute a signature, fit or error.
That is what makes `--from-json` safe and what keeps `results.json`
the single source of truth.

### The results have a machine-readable contract

The `results.json` shape is defined once, as Pydantic models
(`benchmarks/results_models.py`), the same way the package defines its
`schemas/`. `build_results()` validates every run through the models and returns
a canonical dict, so a type leak (a stray `numpy.bool_`, a missing field) fails
the run rather than being written to disk. The committed
`benchmarks/results.schema.json` is a *derived artifact* of those models
regenerated on shape changes and guarded by a drift test — external consumers validate
against it, while the Python types stay the single source of truth. `--from-json`
refuses to render a file the models reject. Consumers can validate any results file.
Try running the script below - if an AssertionError is not raised, the results are
valid against the schema.

```python
from benchmarks import camels_benchmark as cb
import json

results = json.load(open("benchmark-output/results.json"))
errors = cb.validate_results(results)   # [] when valid
assert not errors, errors
```

Bumping the output shape means bumping `SCHEMA_VERSION` (metadata
`schema_version` is `const`-pinned in the schema), so the schema and the
payload can never silently disagree.

### Tolerances (decided up front)

Tolerances are recorded verbatim in `metadata.tolerances` of `results.json` and
are **not loosened when a check fails** — an unmet check is a finding, not a
reason to retune.

| Check | Error | Tolerance | Rationale |
| --- | --- | --- | --- |
| q_mean, q5, q95, runoff_ratio, fdc_slope | relative | 25 % | synthetic series calibrated *to*, not measured from, CAMELS |
| baseflow_index (signatures), BFI (Lyne-Hollick, Eckhardt) | absolute | 0.15 | CAMELS BFI uses a different separation algorithm |
| peak_month | circular | 2 months | month-of-year is circular |
| FFA quantile vs reference (per return period) | relative | 20 % | wider than the Potomac ±10 % because semi-arid / heavy-tailed gauges carry MLE-vs-LM spread |
| q_mean normalised RMSE (aggregate gate) | % | 25 % | across the 10 gauges |
| BFI PBIAS (aggregate gate) | % | 25 % | across the 10 gauges |
| FFA mean relative error (aggregate gate) | % | 20 % | over the dependable cross-checks (GEV-L-moments + LP3) |

### GEV is compared estimator-to-estimator

AquaScope `gev` is compared to the reference `scipy_gev` (plain MLE) even where
the reference fit is unstable (`mle_stable: false`). Those mismatches are
classified `data_limitation` in the results — the data are insufficient for a
stable GEV-MLE, not a defect in either implementation — and are surfaced in the
summary (`n_data_limitation_findings`) rather than hidden. Execution times are
recorded per stage but never asserted, so a slow shared runner cannot produce a
false failure.

### Signature-integrity block

Each catchment also carries an `integrity` block recording internal invariants
on AquaScope's own signature object — `q5 < median < q95`, runoff ratio in
(0, 1), positive recession constant, finite negative FDC slope, all fields
populated. These are the checks the legacy `examples/validation` suite covered
separately; they are surfaced in the report as software defects and are
**never** folded into the headline gates (which stay about published-value
comparisons).

### How the peaks reach the fits

The cached peak series is one value per **USGS water year**
(starts October 1st,ends September 30th).
AquaScope's `flood_analysis` resamples a dated input to calendar-year annual maxima, which
would silently collapse peaks that share a calendar year across two water years
(e.g. a Jan peak in WY2000 and a Dec peak in WY2001). The harness passes the
series on a synthetic unique-year index so the resampler is a no-op and the fits
run on exactly the same annual-maxima set as the reference. The committed
`ffa_reference.json` records a per-gauge `data_quality` block
(`rows_downloaded`, `rows_kept`, why rows were removed, and every qualifier
code seen) so screen provenance is available without re-running the fetch.

## Reference generation (flood-frequency data)

```bash
pip install "aquascope[benchmarks]"      # installs dataretrieval + lmoments3
python benchmarks/fetch_peak_flows.py
```

This is the network step. It fetches USGS annual peaks via `dataretrieval`,
screens them (drops qualifier codes 3/4/8 — dam failure, censored — and
non-positive / sentinel / undated values, dedupes to one value per water year),
caches them under `data/camels_benchmark/peaks/`, and fits GEV-MLE, GEV-L-moments
(lmoments3) and a basic LP3 to publish `data/camels_benchmark/ffa_reference.json`.
It is generation-only; `dataretrieval` and `lmoments3` are not runtime
dependencies of AquaScope.
